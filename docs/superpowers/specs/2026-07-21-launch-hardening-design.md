# 上线稳妥与账号安全加固设计

## 目标

让兑换码用户在服务重启、多人访问和公开部署后，仍能稳定登录、完成邮箱验证并安全使用已购买的会员权益；不改变现有页面视觉、套餐规则、兑换码规则或视频处理能力。

## 范围

本轮只处理以下四类问题：运行配置、账户密码、认证接口防滥用、启动说明。支付、兑换码价格、会员额度、前端页面结构和视频解析流程均不在本轮变更范围内。

## 当前风险

1. `JWT_SECRET` 缺失时会在每次后端启动生成随机值，所有已登录用户会被迫退出。
2. 用户密码目前使用单轮 SHA-256 加盐，计算成本过低，不适合保存付费用户账号密码。
3. 验证码只有“同邮箱 60 秒”冷却；登录接口没有失败次数限制，公开页面容易被撞库或用于刷邮箱。
4. API 同时设置跨域通配符和凭证，无法表达正式站点应当允许的明确来源。
5. 当前 README 没有完整说明 JWT、邮箱、跨域配置和唯一的标准启动方式，容易出现前端连到错误后端的情况。

## 方案

### 1. 运行配置与启动校验

新增 `APP_ENV`，默认值为 `development`。

- 当 `APP_ENV=production` 时，后端启动必须检查以下值：`JWT_SECRET`、`EMAIL_CODE_SECRET`、`CORS_ALLOW_ORIGINS`、`SMTP_HOST`、`SMTP_FROM`。
- 任一值为空时，后端在启动阶段直接报出缺失变量名称并拒绝提供服务；不会回退到随机 JWT 或固定验证码密钥。
- 开发环境保留可启动性，但会在控制台输出安全警告；JWT 和验证码密钥可使用进程内临时值，仅用于本机开发。
- `CORS_ALLOW_ORIGINS` 使用逗号分隔的来源列表。开发默认仅允许 `http://localhost:5173`、`http://127.0.0.1:5173`、`http://localhost:5174`、`http://127.0.0.1:5174`；生产环境不再使用 `*`。
- `backend/.env.example` 增加全部上述配置、用途说明与安全提示，但绝不包含真实密钥或授权码。

### 2. 密码存储与兼容迁移

新密码使用 Python 标准库 `hashlib.pbkdf2_hmac("sha256", ...)`，输出格式：

```text
pbkdf2_sha256$600000$<salt>$<digest>
```

- 新注册和邮箱重置密码的最小长度调整为 8 位。
- 已有 `salt$sha256` 格式的密码仍可登录；首次验证成功后，系统立即将它重写为 PBKDF2 格式，不要求老用户重置密码。
- 错误密码、损坏格式和未知格式统一返回失败，不泄露账号是否存在。
- 不引入额外第三方依赖。

### 3. 验证码与登录防滥用

使用现有 SQLite 数据库新增认证事件表，仅保存动作类型、脱敏范围键和时间戳，不保存密码、验证码或 SMTP 授权码。

- 验证码：保留现有“同邮箱同用途 60 秒”冷却；额外限制同一 IP 在 15 分钟内最多请求 10 次验证码。
- 登录：同一 IP 在 15 分钟内最多允许 10 次失败登录；成功登录不计入失败次数。
- 触发限制时返回 HTTP 429 和明确的“请稍后再试”文案；前端继续展示服务端错误，无需新增页面。
- 认证事件表按时间窗口清理过期数据，避免 SQLite 文件无限增长。
- 限制值通过环境变量覆盖：`AUTH_RATE_LIMIT_WINDOW_SECONDS`、`EMAIL_CODE_IP_MAX_REQUESTS`、`LOGIN_IP_MAX_FAILURES`。

### 4. 标准本地启动与文档

新增根目录 `scripts/start-local.ps1`：默认使用项目根目录 `.venv` 启动后端 `8000` 和前端 `5173`，并在启动后检查 `/api/health`。

- 脚本只负责本地开发，不修改 `.env`、数据库或兑换码数据。
- README 改为 UTF-8 可读的启动章节，说明标准地址、环境变量、QQ 邮箱 SMTP 配置、验证码测试和正式环境必须关闭 `EMAIL_CODE_DEBUG`。
- 临时会话用的 `frontend/vite.session.config.mjs` 保持为本地未跟踪文件，不纳入提交，也不作为标准启动方案。

## 接口与用户影响

- `POST /api/auth/send-code` 与 `POST /api/auth/login` 在触发频率限制时可能新增 HTTP 429；其他成功响应结构不变。
- 设置固定 `JWT_SECRET` 后，已有由随机旧密钥签发的本地登录态会失效一次；用户重新登录后，后续重启不再导致集体退出。
- 旧账号可继续使用原密码登录；新注册和重置密码需要至少 8 位。
- 前端无需改动视觉设计，只需确保错误提示能展示 HTTP 429 返回的 `detail`。

## 验证策略

1. 单元测试覆盖 PBKDF2 新格式、旧 SHA-256 格式兼容登录与成功后的自动迁移。
2. 单元测试覆盖生产配置缺失时的失败、开发配置的可启动性，以及 CORS 白名单解析。
3. 单元测试覆盖邮箱 IP 限制、登录失败限制、成功登录不计入失败次数与窗口过期。
4. 执行全部后端单元测试、前端现有 Node 测试和生产构建。
5. 使用 `EMAIL_CODE_DEBUG=0` 的本地后端进行健康检查；邮件实际投递仍由你在注册页发起一次测试确认。

## 非目标

- 不新增后台管理页面、验证码图形挑战、支付渠道、订单系统或第三方风控服务。
- 不变更会员套餐、兑换码生成方式、游客额度和视频下载授权边界。
- 不将 SMTP 授权码、JWT 密钥、DeepSeek 密钥或用户资料写入仓库。
